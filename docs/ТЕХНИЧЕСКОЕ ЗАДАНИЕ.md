# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Система обнаружения, визуализации, мониторинга и анализа физической L2-топологии сети

**Статус документа:** базовая спецификация продукта  
**Целевые платформы:** legacy Windows 8.1 / Windows Server 2012 и новее; modern backend — поддерживаемые Windows и Linux
**Основной язык интерфейса:** русский  
**Основной язык разработки:** C#  
**Целевая среда выполнения:** .NET Framework 4.8 (legacy); .NET Standard 2.0 (shared core); modern Engine — .NET 8.0 сейчас, целевой production runtime — .NET 10 LTS после обновления toolchain
**Тип приложения:** WPF Windows-клиент + backend host: legacy NetLoom.Service или modern NetLoom.Engine для Windows/Linux

---

# 1. Назначение системы

Разрабатываемая система предназначена для автоматизированного обнаружения, документирования, визуализации, мониторинга и диагностики физической и логической топологии Ethernet-сетей.

Основная задача системы — дать оператору достоверный и понятный ответ на вопросы:

- какие сетевые устройства существуют;
- где физически или логически находится каждое устройство;
- к какому устройству и к какому порту оно подключено;
- какой тип соединения используется;
- какие физические кольца существуют в сети;
- какие порты участвуют в RSTP/STP;
- какие линии в настоящий момент находятся в состоянии Forwarding;
- какие линии заблокированы Spanning Tree;
- какой Bridge является Root Bridge;
- как изменилась топология перед аварией;
- где последний раз наблюдался конкретный IP или MAC;
- какие сведения являются подтверждёнными, а какие построены только на косвенных признаках.

Система не должна позиционироваться как универсальная замена Zabbix, PRTG, LibreNMS или других систем общего мониторинга.

Основная специализация продукта:

**физическая L2-топология + LLDP/CDP + FDB/ARP-корреляция + STP/RSTP + анализ колец + история изменения связей.**

# 2. Основные принципы архитектуры

При разработке должны соблюдаться следующие архитектурные принципы.

## 2.1. Наблюдение не является фактом топологии

Полученная по SNMP запись не должна автоматически становиться физической связью.

Между сетевыми коллекторами и итоговой картой должен существовать слой наблюдений:

```text
Сеть
  ↓
Коллекторы
  ↓
Наблюдения / Evidence
  ↓
Topology Resolver
  ↓
Нормализованная модель сети
  ↓
Карта
```

Например:

```text
MOXA-84 сообщает:

LocalPort = 8
RemoteChassisId = 00:11:22:33:44:55
RemotePort = sfp1
```

Система первоначально должна сохранить это как наблюдение LLDP.

Только Topology Resolver должен определить:

```text
Устройство A / Port8
        ↕
Устройство B / sfp1
```

и присвоить связи уровень достоверности.

# 4. Идентичность устройства

IP-адрес запрещается использовать как постоянный первичный идентификатор устройства.

Каждое обнаруженное устройство получает внутренний:

```text
DeviceId = GUID
```

IP является одним из изменяемых атрибутов.

Для идентификации устройства необходимо использовать набор Identity Claims:

- serial number;
- LLDP Chassis ID;
- chassis MAC;
- management MAC;
- SNMP sysObjectID;
- SNMP sysName;
- hostname;
- management IP;
- другие доступные идентификаторы.

Пример:

```text
DeviceId:
4c698338-...

CustomName:
Коммутатор серверной

ManagementIP:
10.48.228.84

sysName:
MOXA-09801

LLDP Chassis ID:
00:90:E8:...

Serial:
ABCD12345
```

Следует учитывать, что LLDP Chassis ID не обязан быть MAC-адресом.

Он может представлять:

- MAC;
- network address;
- interface name;
- locally assigned identifier;
- другой тип идентификатора.

При конфликте Identity Claims запрещается автоматически объединять устройства без достаточных оснований.

Должны существовать ручные операции:

- «Объединить устройства»;
- «Разделить ошибочно объединённое устройство».

Пользовательское название устройства должно сохраняться независимо от:

- изменения IP;
- изменения sysName;
- перезагрузки;
- временной недоступности.

# 6. Ручные неуправляемые устройства

Система обязана поддерживать ручное создание устройств, которые невозможно обнаружить средствами SNMP, LLDP, CDP или IP.

Это требуется, например, для:

- тупых медиаконверторов;
- unmanaged switch;
- оптических преобразователей;
- пассивных сетевых устройств;
- промежуточного оборудования;
- неизвестных соединительных устройств.

Пользователь должен иметь возможность:

- создать такое устройство;
- присвоить ему имя;
- выбрать тип;
- выбрать форму отображения;
- указать число виртуальных портов;
- дать портам названия;
- вручную нарисовать соединения;
- указать тип каждого соединения;
- добавить комментарий;
- указать объект размещения.

Ручное устройство получает:

```text
DiscoverySource = Manual
MonitoringCapability = None
```

Оно не должно автоматически считаться Offline.

Статус такого устройства:

```text
Не контролируется
```

или:

```text
Нет данных
```

Ручные устройства и ручные линии обязательно должны участвовать в алгоритме поиска физических циклов.

Таким образом, вручную добавленный медиаконвертор может стать частью обнаруженного физического кольца.

Ручной элемент запрещается удалять в результате автоматического Discovery.

# 7. Объекты и физическое размещение

Для повышения читаемости карты должна существовать отдельная система объектов размещения.

Примеры:

```text
Площадка
 ├── Офис 1
 │    ├── Серверная
 │    └── Кабинет 101
 │
 ├── Офис 2
 │    ├── Серверная
 │    └── Узел связи
 │
 └── Котельная
```

Система должна поддерживать вложенные Location.

Минимальные типы:

- площадка;
- объект;
- здание;
- помещение;
- серверная;
- шкаф;
- пользовательская группа.

На карте Location отображается как крупная прямоугольная область с подписью.

Например:

```text
┌──────────────────────── ОФИС 1 ────────────────────────┐
│                                                        │
│   [SW-01] ───────── [MOXA-01]                         │
│                                                        │
│                      [Server-01]                       │
│                                                        │
└────────────────────────────────────────────────────────┘
```

Функции объекта:

- изменение размера;
- перемещение;
- переименование;
- цвет/фон;
- комментарий;
- блокировка положения;
- сворачивание;
- разворачивание;
- вложенность;
- скрытие.

При перемещении объекта пользователь может выбрать:

```text
Переместить только рамку
```

или:

```text
Переместить рамку вместе с устройствами
```

Устройство может принадлежать одному основному Location.

Линии между различными Location должны оставаться видимыми.

# 8. Визуальная карта

Главный интерфейс системы должен представлять собой простую псевдографическую карту.

Не требуется сложная трёхмерная или дизайнерская визуализация.

Основные элементы:

- прямоугольники;
- скруглённые прямоугольники;
- круги;
- простые иконки;
- линии;
- текстовые подписи;
- рамки объектов.

Цель интерфейса:

**максимальная информативность при минимальной визуальной сложности.**

---

# 9. Узлы карты

Узел должен отображать как минимум:

```text
Пользовательское имя
IP
sysName или модель
Статус
```

Пример:

```text
┌─────────────────────┐
│ Коммутатор Офис 1   │
│ 10.48.228.84        │
│ MOXA EDS-408A       │
└─────────────────────┘
```

Допускаются различные формы:

- квадрат;
- прямоугольник;
- круг;
- скруглённый прямоугольник;
- пользовательский простой символ.

Форму допускается назначать:

- автоматически;
- вручную.

---

# 10. Цветовые состояния устройства

Цвет не должен быть единственным способом передачи статуса.

Всегда должна существовать текстовая расшифровка.

Предусмотреть следующие итоговые состояния:

```text
Доступен
Частично доступен
Наблюдается косвенно
Недоступен
Нет данных
Мониторинг отключён
Не контролируется
```

При этом внутренне должны отдельно храниться:

```text
ICMP
SNMP
TCP
LLDP Seen
CDP Seen
FDB Seen
ARP Seen
LastSeen
```

Например:

```text
ICMP: недоступен
SNMP: доступен
TCP/443: доступен
```

не должно приводить к статусу:

```text
Устройство недоступно
```

# 11. Редактирование карты

Пользователь должен иметь возможность:

- перемещать устройство мышью;
- перемещать группы;
- создавать ручные узлы;
- создавать ручные линии;
- удалять ручные элементы;
- редактировать подписи;
- изменять пользовательское название;
- добавлять заметки;
- изменять форму;
- изменять размер;
- фиксировать положение;
- скрывать элемент;
- показывать скрытые элементы;
- масштабировать карту;
- перемещать рабочую область.

Координаты устройств сохраняются в БД.

Автоматическое обновление топологии запрещается использовать как повод для изменения положения уже существующих узлов.

---

# 12. Автоматическое размещение

Сложная автоматическая компоновка графа не является обязательной функцией MVP.

Для нового устройства используется простая стратегия:

1. найти известного физического соседа;
2. разместить новое устройство рядом с ним;
3. проверить наличие свободной области;
4. если сосед неизвестен — поместить устройство в область «Новые устройства».

Должна существовать функция:

```text
Зафиксировать расположение
```

После фиксации автоматический Discovery не имеет права перемещать существующие элементы.

---

# 13. Обнаружение устройств

Discovery не должен основываться только на ICMP.

ICMP является лишь одним из источников наблюдений.

Поддерживаются:

- seed-IP;
- диапазон CIDR;
- ручной IP;
- SNMP;
- разрешённый TCP Connect;
- LLDP-соседи;
- CDP-соседи;
- ARP;
- FDB;
- DNS;
- ручное добавление.

Пример:

```text
10.48.228.0/24
```

может быть профилем Discovery.

---

# 14. Безопасность Discovery

Категорически запрещается:

- автоматически перебирать SNMP community strings;
- подбирать пароли;
- автоматически проверять стандартные credentials;
- выполнять SNMP SET;
- выполнять произвольные команды;
- запускать агрессивное сканирование без явного разрешения оператора.

Система представляет собой диагностический read-only инструмент.

```text
Да

********

1500 мс

```

Профиль содержит:

# 16. SNMP

Обязательная поддержка:

- SNMP v1;
- SNMP v2c;
- SNMP v3.

Основные стандартные данные:

- sysDescr;
- sysObjectID;
- sysUpTime;
- sysName;
- sysLocation;
- ifTable;
- ifXTable;
- BRIDGE-MIB;
- LLDP-MIB;
- доступные RSTP/STP MIB;
- ARP/neighbor tables;
- FDB tables.

Опрос должен использовать только необходимые OID.

Полный SNMP Walk не должен выполняться постоянно без необходимости.

---

# 17. LLDP

LLDP является основным источником физической L2-топологии.

Необходимо сохранять:

- local chassis;
- local port;
- remote chassis;
- remote port;
- remote sysName;
- remote port description;
- management address;
- время наблюдения;
- исходные raw значения.

Следует учитывать, что LLDP local port number не обязан совпадать с ifIndex.

Необходимо выполнить корректное сопоставление LLDP port ↔ Interface.

При невозможности однозначного сопоставления результат помечается соответствующей достоверностью.

---

# 18. CDP

Для Cisco должна поддерживаться работа с CDP.

Сохраняются:

- remote Device ID;
- remote port;
- local interface;
- management address;
- platform;
- capabilities;
- timestamp.

CDP и LLDP рассматриваются как независимые источники evidence.

---

# 19. FDB

Система должна собирать MAC forwarding tables.

Важно:

```text
MAC виден на Port8
```

не означает:

```text
MAC физически подключён непосредственно к Port8
```

Следовательно, FDB Observation хранится отдельно от PhysicalLink.

Пример:

```text
MAC:
00:11:22:33:44:55

SeenBehind:
MOXA-84 / Port8
```

Только Topology Resolver имеет право использовать эту информацию для inference.

---

# 20. Mapping Bridge Port → ifIndex

FDB и STP используют bridge-port index.

Категорически запрещается предполагать:

```text
BridgePortIndex == ifIndex
```

Для сопоставления необходимо использовать:

```text
dot1dBasePortIfIndex
```

Алгоритм:

```text
Bridge Port
     ↓
dot1dBasePortIfIndex
     ↓
ifIndex
     ↓
Interface
```

Это правило является обязательным для всех соответствующих модулей.

---

# 21. ARP/IP correlation

Система должна уметь связывать:

```text
IP
 ↓
ARP
MAC
 ↓
FDB
Switch / Port
```

Это особенно необходимо для оборудования:

- Cisco ASA;
- С-Терра;
- закрытых маршрутизаторов;
- серверов;
- устройств с отключённым ICMP;
- устройств без доступного SNMP.

Результат должен отображаться как косвенное наблюдение.

Например:

```text
10.48.228.15
MAC: xx:xx:xx:xx:xx:xx
виден за MOXA-84 / Port3

Достоверность:
Предполагаемая
```

---

# 22. Модель достоверности

У связи должны существовать отдельно:

## Strength

```text
Confirmed
Observed
Inferred
Manual
```

## Freshness

```text
Current
Stale
```

`Stale` не является источником связи.

Например:

```text
Strength = Confirmed
Freshness = Stale
```

означает:

«Связь ранее была подтверждена LLDP с двух сторон, но давно не подтверждалась».

---

# 23. Confirmed Link

Связь считается Confirmed, если имеется достаточно согласованных наблюдений.

Наиболее надёжный вариант:

```text
A говорит:
A/P1 → B/P5

B говорит:
B/P5 → A/P1
```

Topology Resolver объединяет два observations в одну PhysicalLink.

---

# 24. Observed Link

Односторонний LLDP/CDP:

```text
A/P1 → B/P5
```

без подтверждения с B.

Такая связь существует на карте, но должна иметь статус:

```text
Observed
```

---

# 25. Inferred Link

Связь, построенная на основе:

- FDB;
- ARP;
- OUI;
- комбинации нескольких таблиц;
- косвенного анализа,

получает:

```text
Inferred
```

Такая линия визуально отличается от подтверждённой.

---

# 26. Manual Link

Пользователь может вручную зафиксировать:

```text
MOXA Port8
    ↕
MediaConverter Port1
```

или любую другую связь.

Она получает:

```text
Strength = Manual
```

Автоматический Discovery не должен её удалять.

При обнаружении противоречия система должна показать предупреждение оператору.

---

# 27. STP / RSTP

Система должна собирать и сохранять Spanning Tree observations.

Минимально:

- Bridge ID;
- Root Bridge ID;
- root path cost;
- topology changes;
- bridge port;
- mapped ifIndex;
- state;
- timestamp.

Поддерживаемые состояния:

```text
Disabled
Blocking
Listening
Learning
Forwarding
Broken
Unknown
```

Для пользовательского интерфейса допускается нормализованное название:

```text
Blocking / Discarding
```

при обязательном сохранении исходного raw значения.

---

# 28. Port Role

Port Role должен собираться только если он действительно предоставляется соответствующим стандартным или vendor-specific MIB.

При отсутствии данных:

```text
Role = Unknown
```

Запрещается выдавать предположение за фактическую роль.

---

# 29. MSTP-ready архитектура

Состояние STP запрещается хранить как единственное:

```text
Interface.RstpState
```

Необходимо использовать сущность:

```text
StpObservation
```

с полями:

```text
DeviceId
InterfaceId
BridgePortIndex
Protocol
InstanceId
PortState
PortRole
RootBridgeId
DesignatedBridgeId
PathCost
ObservedAt
RawValue
```

Даже если первая версия работает только с CIST/RSTP, архитектура должна позволять позднее добавить MSTI.

---

# 30. Анализ физических колец

Topology Analyzer должен рассматривать физическую топологию как граф:

```text
G = (Devices, PhysicalLinks)
```

Необходимо реализовать поиск циклов.

Каждое найденное кольцо получает:

```text
RingId
```

и перечень:

- устройств;
- интерфейсов;
- линий.

Пример:

```text
Кольцо №3

MikroTik-146/SFP
→ MOXA-84/P8
→ MikroTik-147/SFP
→ MikroTik-146/SFP
```

Ручные устройства и ручные связи также входят в этот граф.

---

# 31. Анализ защиты кольца

Для каждого обнаруженного физического цикла система должна попытаться определить:

- есть ли STP/RSTP;
- существует ли Blocking/Discarding port;
- кто Root Bridge;
- существует ли несколько потенциальных blocking points;
- существует ли кольцо, в котором все известные порты находятся Forwarding.

Последняя ситуация является важным предупреждением.

Пример:

```text
ПРЕДУПРЕЖДЕНИЕ

Обнаружено физическое кольцо №4.

Ни на одном из доступных портов
не обнаружено состояние Blocking/Discarding.
```

При недостатке данных сообщение должно говорить:

```text
Невозможно подтвердить наличие защиты от петли.
```

а не утверждать наличие аварии.

---

# 32. Режимы карты

Карта должна иметь как минимум три режима.

## Физическая топология

Показываются все известные физические соединения.

## Активное STP-дерево

Основной акцент делается на Forwarding path.

Blocking/Discarding links отображаются отдельным стилем.

## Достоверность

Линии оформляются в зависимости от:

```text
Confirmed
Observed
Inferred
Manual
Stale
```

---

# 33. Подписи линий

Линия может отображать:

```text
Port8 ↔ sfp1
Оптика
1 Гбит/с
RSTP: Blocking
```

Обязательные данные:

- local port;
- remote port.

Опционально:

- media;
- speed;
- VLAN;
- STP state;
- confidence.

Количество отображаемой информации должно регулироваться настройкой карты.

---

# 34. Тип линии

Поддерживаются:

```text
Медь
Оптика
Беспроводная
Логическая
Неизвестно
Пользовательский тип
```

Автоматическое определение типа линии рассматривается как предположение.

Пользователь имеет право вручную исправить тип.

Ручное значение имеет приоритет для визуализации, но автоматическое observation сохраняется отдельно.

---

# 35. Мониторинг

Мониторинг не должен обязательно работать постоянно.

Это принципиальное требование.

Должны существовать четыре режима:

```text
Отключён
Только вручную
По расписанию
Постоянный периодический
```

---

# 36. Глобальное управление мониторингом

В основном интерфейсе должны присутствовать кнопки:

```text
Запустить мониторинг
Остановить мониторинг
Опросить сейчас
Обновить топологию сейчас
```

При отключении мониторинга система прекращает активные опросы оборудования.

Сохранённая карта остаётся доступной.

Статусы не должны автоматически становиться красными.

Они получают признак:

```text
Мониторинг остановлен
```

с отображением времени последнего опроса.

---

# 37. Расписание мониторинга

Пользователь должен иметь возможность настроить, например:

```text
Понедельник–Пятница
08:00–18:00
```

или:

```text
Каждый день
02:00
Topology Discovery
```

или:

```text
Health Check
каждые 5 минут
только с 07:00 до 19:00
```

Расписание сохраняется и работает независимо от открытого UI.

---

# 38. Раздельные циклы мониторинга

Должно существовать не менее трёх классов задач.

## Health Check

Быстрый.

Например:

- ICMP;
- sysUpTime;
- минимальный SNMP GET;
- разрешённые TCP checks.

## Interface Monitoring

Средняя частота.

Например:

- ifOperStatus;
- ifAdminStatus;
- ошибки;
- выбранные интерфейсные counters.

## Topology Discovery

Редкий.

Например:

- LLDP;
- CDP;
- FDB;
- ARP;
- STP;
- identity reconciliation.

Каждый класс имеет собственное расписание.

---

# 39. Мониторинг отдельных устройств и объектов

Мониторинг должен включаться/выключаться:

- глобально;
- для AccessProfile;
- для объекта;
- для устройства.

Например:

```text
Офис 1:
мониторинг включён

Офис 2:
только ручной опрос

С-Терра:
активный опрос запрещён
```

---

# 40. Безопасное ограничение нагрузки

Для каждого AccessProfile:

- maximum parallel requests;
- timeout;
- retries;
- delay;
- schedule.

Глобально должен существовать maximum parallelism.

Для старого промышленного оборудования должны поддерживаться консервативные настройки.

Пример:

```text
Параллельных устройств:
3

Timeout:
2000 мс

Retries:
1

Topology Discovery:
раз в 6 часов
```

---

# 41. Работа с частичными ошибками

Ошибка одного OID не должна приводить к провалу всего устройства.

Например:

```text
sysName: OK
ifTable: OK
LLDP: timeout
RSTP: unsupported
```

Результат должен сохраняться частично.

---

# 42. Повторные попытки

Стратегия Retry должна быть управляемой.

Пример:

```text
Timeout = 1500 мс
Retries = 2
Delay = 300 мс
```

Необходимо избегать синхронного массового повторного опроса всех устройств.

Желателен небольшой jitter.

---

# 43. Устройства без ICMP

ICMP timeout не означает:

```text
Offline
```

Если доступны:

- SNMP;
- TCP;
- LLDP observation;
- FDB observation,

устройство отображается соответствующим образом.

---

# 44. Устройства без прямого доступа

Для Cisco ASA, С-Терра и аналогичного оборудования система может располагать только:

- IP;
- MAC;
- OUI;
- DNS name;
- соседним LLDP;
- FDB;
- ARP;
- ручным описанием.

Это считается допустимым состоянием.

Система не должна пытаться получить дополнительные сведения неразрешёнными методами.

---

# 45. Vendor Adapter

Специфика производителей инкапсулируется в отдельных адаптерах.

Минимально предусмотреть:

```text
GenericAdapter
MoxaAdapter
MikroTikAdapter
CiscoAdapter
CTerraAdapter
```

GenericAdapter всегда используется первым.

Vendor Adapter добавляет особенности, но не должен заменять стандартный путь без необходимости.

---

# 46. MOXA

Следует учитывать:

- различия между сериями;
- возможный Turbo Ring;
- различия прошивок;
- старые реализации SNMP;
- неполный LLDP;
- различные обозначения портов;
- возможные vendor MIB.

Нельзя автоматически предполагать наличие RSTP только по модели.

---

# 47. Turbo Ring

Поддержка анализа Turbo Ring рассматривается как отдельный vendor-specific модуль.

Если система точно определяет наличие Turbo Ring, она должна отображать это отдельно от стандартного RSTP.

Запрещается интерпретировать Turbo Ring как обычный RSTP без подтверждения.

---

# 48. MikroTik

Поддержать RouterOS и, по возможности, SwOS с учётом различий доступных MIB.

Vendor-specific код не должен попадать в общий Topology Resolver.

---

# 49. Cisco

Поддержать:

- LLDP;
- CDP;
- стандартный SNMP;
- доступные bridge/STP данные;
- Cisco-specific identification.

Cisco ASA не должна автоматически рассматриваться как обычный L2-коммутатор.

---

# 50. История

Необходимо разделять:

```text
Current State
```

и:

```text
History
```

Не требуется бесконечно сохранять каждое значение каждой метрики.

История должна в первую очередь хранить изменения.

---

# 51. Network Event

Минимальные типы событий:

```text
Устройство обнаружено
Устройство перестало отвечать
Устройство снова доступно
SNMP недоступен
SNMP восстановлен

Порт поднялся
Порт упал

Обнаружен новый сосед
Сосед исчез
Сосед на порту изменился

Создана новая физическая связь
Связь перестала подтверждаться

STP State changed
Root Bridge changed
Topology Change detected

MAC moved
Possible MAC flapping

Обнаружено новое кольцо
Кольцо исчезло
Изменилась точка блокировки кольца

Изменился management IP
Изменился sysName
```

---

# 52. Корреляция событий

Система должна позволять анализировать события в общей временной шкале.

Пример:

```text
12:41:02  Root Bridge changed
12:41:02  Topology Change
12:41:03  Port7 Forwarding → Blocking
12:41:03  MAC moved
12:41:04  10.48.228.147 SNMP timeout
12:41:08  Port7 Blocking → Forwarding
12:41:09  10.48.228.147 доступен
```

На основании последовательности система может формировать:

```text
Возможная корреляция событий
```

но не должна автоматически объявлять причинно-следственную связь без доказательств.

---

# 53. MAC flapping

При наличии последовательности быстрых перемещений одного MAC между портами должно генерироваться событие:

```text
Возможный MAC flapping
```

Порог и временное окно настраиваются.

---

# 54. Topology Snapshot

Система должна поддерживать снимки топологии.

Snapshot содержит состояние:

- Devices;
- Links;
- Locations;
- STP;
- Root Bridge;
- Ring list;
- confidence;
- timestamp.

Должна существовать функция сравнения двух snapshots.

Пример:

```text
Добавлено:
1 устройство
2 линии

Удалено:
1 линия

Изменено:
Root Bridge
3 состояния портов
```

---

# 55. Stale

Устройство или связь запрещается удалять после одного неудачного опроса.

Хранятся:

```text
FirstSeen
LastSeen
LastConfirmed
FailureCount
```

После заданного времени объект получает:

```text
Stale
```

Удаление:

- только вручную;
- либо отдельной политикой retention.

По умолчанию автоматическое физическое удаление запрещено.

---

# 56. Поиск

Поиск должен поддерживать:

- IP;
- MAC;
- hostname;
- sysName;
- CustomName;
- serial;
- vendor;
- model;
- interface.

Особая функция:

```text
Где находится MAC?
```

Должна показывать все последние FDB observations.

```text
Создать резервную копию
```

# 66. MVP и первая реализация

Допускается первоначально разместить Service и UI внутри одного процесса для ускорения разработки.

```text
Collector → WPF
```

Collector должен возвращать model/domain objects.

UI является потребителем модели.

# 67. Технологический стек

Базовый:

```text
C#
.NET Framework 4.8
WPF
SQLite
SNMP library
Named Pipes (Windows transport implementation)
Task Parallel Library
SemaphoreSlim
```

Запрещается без необходимости увеличивать количество сторонних зависимостей.

Каждая новая dependency должна иметь техническое обоснование.

# 68. Работа с SQLite

SQLite является основной БД.

Обязательно:

- SchemaVersion;
- миграции;
- индексы;
- foreign keys;
- транзакции;
- backup;
- WAL при подтверждённой совместимости.

Схему БД нельзя менять без предварительного анализа возможности использовать существующие таблицы.

---

# 69. UI и БД

UI в конечной архитектуре не должен самостоятельно изменять SQLite.

Запись выполняет Service.

UI передаёт команды Service.

Это снижает риск:

- lock;
- race conditions;
- повреждения данных.

---

# 70. Производительность

Целевая начальная эксплуатация:

```text
до 500 устройств
до 5000 интерфейсов
до 10000 наблюдаемых связей/evidence
```

Система не обязана конкурировать с Zabbix на десятках тысяч устройств.

---

# 71. Рендеринг

Для небольших карт допустимы WPF Controls.

При увеличении количества линий рекомендуется:

- узлы — WPF Controls;
- линии — DrawingVisual или общий drawing layer.

Не следует создавать тысячи тяжёлых TextBlock/Line, если это начинает влиять на производительность.

---

# 72. Кэш

Collector должен поддерживать кэш текущего состояния.

UI обновляется только при изменении соответствующих свойств.

Topology Discovery должен быть инкрементальным.

---

# 73. Режим симуляции

Обязательная функция разработки.

Система должна уметь работать без реальной сети.

Рекомендуемый формат simulator:

не готовые объекты NetworkNode, а сохранённые raw responses.

Например:

```text
SNMP VarBind snapshot
LLDP snapshot
FDB snapshot
STP snapshot
```

Это позволяет тестировать настоящий parser и Topology Resolver.

---

# 74. Raw evidence

При диагностике сложных случаев должна существовать возможность посмотреть исходные данные.

Например:

```text
OID
Raw value
Timestamp
Source device
```

Это существенно облегчает поиск ошибок MIB и vendor-specific поведения.

# 75. Русский интерфейс

Абсолютно весь пользовательский интерфейс должен быть русскоязычным.

Русскими должны быть:

- меню;
- кнопки;
- сообщения;
- ошибки;
- предупреждения;
- статусы;
- настройки;
- справка;
- журнал сетевых событий.

Официальные технические названия сохраняются:

```text
LLDP
RSTP
SNMP
ifIndex
sysName
OID
Forwarding
```

При необходимости рядом указывается русская расшифровка.

---

# 76. Комментарии исходного кода

Все комментарии в собственном исходном коде проекта должны быть на русском языке.

Это относится к:

- `//`;
- `/* */`;
- XML documentation;
- пояснениям сложных алгоритмов;
- TODO/FIXME.

Идентификаторы классов, методов и переменных рекомендуется оставлять английскими.

Например:

```csharp
// Сопоставляем bridge-port с физическим ifIndex.
// Нельзя считать, что эти значения совпадают.
private int ResolveInterfaceIndex(...)
```

Это является обязательным coding rule.

# 77. Пользовательские строки

Пользовательские строки рекомендуется вынести в централизованные Resources.

Даже если в первой версии существует только русский язык.

Это исключит разбрасывание текстов по code-behind.

# 78. Ошибки

Программа не должна завершаться из-за:

```text
Protocol
OID, если применимо
Exception
Attempt
```

# 83. Критерии приёмки архитектуры

До начала крупной разработки должны выполняться следующие условия:

1. IP не является DeviceId.
2. Observation отделён от PhysicalLink.
3. FDB Observation не является PhysicalLink.
4. bridge-port не считается ifIndex.
5. UI не является частью Collector.
6. ручной элемент не удаляется Discovery.
7. stale data не удаляется автоматически.
8. monitoring можно полностью выключить.
9. Discovery имеет rate limits.
10. никакого credential guessing.
11. все пользовательские тексты русские.
12. все комментарии собственного кода русские.

# Архитектурное уточнение — cross-platform deployment

Этот раздел имеет приоритет над более ранними Windows-only формулировками ТЗ в части runtime, backend host и IPC.

- Shared core (`NetLoom.Domain`, `NetLoom.Application`, `NetLoom.Contracts`, `NetLoom.Topology`) — `netstandard2.0`.
- `NetLoom.Protocols.Snmp` и `NetLoom.Persistence.Sqlite` — `net48;net8.0`.
- `NetLoom.Service` и `NetLoom.Wpf` остаются `net48` для legacy Windows 8.1.
- `NetLoom.Engine` — modern Windows/Linux host; сейчас `net8.0`, целевой production runtime — .NET 10 LTS после обновления toolchain.
- WPF остаётся Windows-only клиентом. После service split UI не пишет SQLite напрямую.
- IPC определяется transport-neutral контрактами; Named Pipes — только локальная Windows-реализация транспорта.
- DPAPI остаётся Windows-реализацией `ISecretProtector`; Linux secret protector реализуется отдельно.
- Основной Engine остаётся на C#/.NET; Go допускается только как возможный будущий `NetLoom.Probe`.

## Topology Resolver v1

Система должна отделять наблюдения протоколов от подтверждённого факта физического соединения.

Topology Resolver формирует промежуточные `PhysicalLinkCandidate` с объяснимым набором evidence.

Требования:

## Lifecycle и stale topology

## Sprint 15 - materialized physical topology

Discovered and manually entered elements use one common physical graph.

Devices, interfaces and physical links use internal GUID identities. An IP address is not a DeviceId.

A manual unmanaged device uses DiscoveryOrigin = Manual and MonitoringCapability = None.

A manual interface uses ifIndex = null and IsManual = true.

A manual physical link uses PhysicalLinkStrength = Manual.

Automatic discovery must not delete or replace manual topology without an explicit user action.

Manual and automatic elements participate in the same topology analysis, including future cycle and ring detection.

Persistent Device-to-Location assignment uses internal DeviceId, not an IP address or a map presentation key.

A manual user action uses the common observation model: ObservationKind.Manual and SourceAddress = User.

## Sprint 26B — ограниченное хранение raw observations

1. Raw SNMP/protocol observations должны иметь ограниченное по времени хранение в topology/configuration SQLite.

## Sprint 27 — анализ безопасности физического графа без зависимости от cycle basis

1. Источником физической adjacency является только materialized `PhysicalLink`.
2. Анализ должен работать как undirected multigraph по stable DeviceId и сохранять distinct parallel PhysicalLink.
3. Reverse/duplicate representation одного LinkKey должна дедуплицироваться.
4. Archived link исключается; hidden/stale/manual link остаётся физическим фактом; self-device link игнорируется.
5. Graph bridge должен определяться с учётом identity конкретного edge, чтобы parallel links не становились ложными bridges.
6. Для каждого eligible PhysicalLink должен быть доступен direction-neutral failure impact.
7. Для bridge result должен содержать две disconnected partitions исходной connected component после удаления link и число разделённых пар устройств.
8. Для non-bridge blast radius равен нулю; направление "пострадавшей стороны" без root/service context не угадывается.
9. STP не создаёт и не удаляет PhysicalLink, а только классифицирует forwarding state существующего physical edge.
10. Forwarding link подтверждается только при однозначной stable InterfaceId binding на обоих endpoint и `Forwarding` на обоих STP ports.
11. `Blocking`/`Disabled` считается confirmed non-forwarding только при однозначно разрешённых обоих endpoint.
12. Missing/ambiguous endpoint, snapshot или port, а также Unknown/Listening/Learning/Broken должны давать unresolved state.
13. Forwarding-loop result не должен зависеть от fundamental cycle basis. Он содержит все confirmed-forwarding PhysicalLink, принадлежащие хотя бы одному cycle.
14. Incomplete STP coverage должна быть явно видна; отсутствие confirmed cycle при incomplete coverage не является доказательством безопасности.
15. Parallel forwarding pair является 2-edge forwarding cycle без интерпретации LAG/vendor ring/RSTP protection.
16. `PhysicalCycleBasisDetector` не является input/source of truth для Sprint 27.
17. Analyzer должен быть deterministic, read-only и не использовать IP/source_address, FDB/ARP или vendor ring protocols как physical adjacency.
18. Sprint 27 не вводит Migration012 и не меняет UI/persistence write paths.

## Sprint 28 — операторская семантика физических колец

1. Fundamental cycle basis не является пользовательским списком именованных колец.
2. Sprint 25 primitive должен называться `PhysicalCycleBasisElement` / `PhysicalCycleBasisDetector`; его идентификатор — `CycleKey`.
3. Пользовательская семантика redundancy должна вычисляться отдельно через `PhysicalRedundancyRegion`.
4. Region должен быть maximal vertex-biconnected block materialized PhysicalLink multigraph.
5. Region detection должен быть basis-independent и не перечислять все simple cycles.
6. Источник adjacency — только materialized PhysicalLink.
7. Один LinkKey дедуплицируется; distinct parallel PhysicalLink сохраняются.
8. Archived исключается; hidden/stale/manual остаются membership facts.
9. `SimpleRing` — block минимум с 3 devices, edge count = device count и degree каждой вершины = 2.
10. Только `SimpleRing` является named-ring candidate.
11. Два или более parallel PhysicalLink между двумя devices классифицируются как `ParallelLinks`, а не как пользовательское кольцо.
12. Chorded/dense/overlapping-by-edge block классифицируется как `Composite`; UI не должен выбирать произвольный simple cycle и объявлять его ring identity.
13. Два ring blocks, разделённые articulation device, остаются разными regions.
14. RegionKey вычисляется из sorted stable PhysicalLink.Id и не зависит от traversal или fundamental basis.
15. Endpoint refinement при сохранении PhysicalLink.Id и membership не меняет RegionKey.
16. STP/RSTP, ForwardingCycleAnalysis, FDB/ARP/IP и vendor ring protocols не формируют region membership.
17. Freshness/evidence остаются отдельными от membership.
18. Per-ring protection label не вводится до следующего Ring protection analyzer.
19. Sprint 28 не меняет SQLite schema, MapSnapshot/WPF и не вводит Migration012.

## Sprint 29 — анализ защиты физического кольца

1. Анализ защиты применяется только к `PhysicalRedundancyRegionKind.SimpleRing`.
2. `ParallelLinks` и `Composite` возвращают `NotApplicable`.
3. STP/RSTP не меняет membership region.

10. Link Disabled имеет приоритет над Blocking/Forwarding.
11. Link Blocking — минимум один Blocking endpoint при отсутствии Disabled/Unresolved.
12. Link Forwarding — оба endpoint Forwarding.
13. `Protected`: полное покрытие, ровно один Blocking PhysicalLink, остальные Forwarding.
14. `Unprotected`: полное покрытие, все PhysicalLink Forwarding.
15. `Degraded`: полное покрытие, есть Disabled или больше одного Blocking PhysicalLink.
16. `Unresolved`: хотя бы один member link не классифицирован однозначно.
17. Disabled не считается intentional protection block.
18. Manual/unmanaged link без InterfaceId должен давать Unresolved, а не ложный status.
19. Stale/Hidden/Manual membership не удаляется и не меняется analyzer'ом.
20. Result должен содержать PhysicalLinkId по Forwarding/Blocking/Disabled/Unresolved buckets.
21. Analyzer read-only, deterministic и не использует IP/source_address, FDB/ARP или vendor ring protocol.
22. Sprint 29 не вводит Migration012 и не меняет WPF/Engine/persistence.

## Sprint 30A — backend поиска MAC/IP

Для поиска MAC/IP приложение должно сохранять явную optional связь protocol observation со stable NetLoom DeviceId, когда такой DeviceId передан в monitoring request.

Требования:

- IP и `source_address` не являются DeviceId;
- FDB `bridgePortIndex` не является ifIndex;
- ifIndex получается только через сохранённый `dot1dBasePortIfIndex`;
- stable InterfaceId получается только по `(DeviceId, ifIndex)`;
- неоднозначный bridge-port mapping не разрешается автоматически;
- отсутствие observation binding или materialized interface должно быть явно отражено в результате;
- IP lookup использует ARP только как IP→MAC evidence;
- FDB используется как MAC sighting evidence и не создаёт PhysicalLink;
- несколько sightings не должны автоматически превращаться в один «правильный access-port»;
- результат обязан содержать freshness/evidence timestamps;
- raw retention удаляет observation binding каскадно;
- пользовательский WPF интерфейс поиска реализуется после стабилизации backend contract.

## Sprint 30B — пользовательский поиск MAC/IP

WPF должен предоставлять локализованный поиск по MAC- или IP-адресу поверх read-only lookup contract.

Требования:

- ввод автоматически классифицируется как IP или MAC только после успешной нормализации;
- malformed input не запускает backend lookup;
- отображаются все returned candidates, включая ambiguity/unresolved;
- для каждого кандидата доступны status, MAC/IP, stable DeviceId/InterfaceId при наличии, ifIndex/bridgePort и timestamps/source ARP/FDB evidence;
- `MapNode.Key` не используется как DeviceId;
- materialized `MapNode.DeviceId` используется только для stable device navigation;
- при `ResolvedInterface` карта подсвечивает device node, а InterfaceId/ifIndex показываются отдельно;
- отсутствие interface-level visual contract запрещает выдумывать port highlight;
- FDB sighting не объявляется автоматически конечным access-port;
- WPF не пишет SQLite и не меняет topology;
- все пользовательские строки находятся в локализационных ресурсах;
- новая migration не требуется; Migration012 остаётся последней.
